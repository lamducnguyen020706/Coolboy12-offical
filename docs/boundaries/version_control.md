## The Boundary

> **A commit records *that a file changed*. It never records *what canonically changed*.**

Version control is the history of the repository's files. It is not the history of the world,
and it is not the history of any Record. Blueprint §26.2e states the distinction and I-85 makes
it an invariant:

> **(scoped v0.7.0)** Version control records that files changed; a Record Model's own temporal
> mechanism — the History Record and WSV-H in World — records what canonically changed and why.
> Semantic history is never reconstructed from a commit log. Correlation may be recorded in one
> direction only, from history entry to commit.

**The distinction is not about capability, it is about *subject*.** A commit history can tell you
a character's file was edited eleven times. Only History Record can tell you which of those
eleven were canonical revisions, which were formatting, which were reverted, and what the world
was before each.

## What Version Control Genuinely Provides

Per Blueprint §26.2e, and coolboy12 should use all of it:

- repository versioning
- rollback
- commit identity
- implementation history
- integrity of file contents

## What It Must Never Be Treated As Providing

Per Blueprint §26.2e:

- History Record
- WSV-H
- semantic history
- canon state

## Three Histories, Never Merged

| History | Answers |
|---|---|
| **History Record** | the history of Record changes |
| **WSV-H** | the history of world-state transitions |
| **Version control** | the history of the repository's files |

They answer three different questions, and a system that merges any two of them has lost the
ability to answer at least one.

## Correlation Is One-Directional

Where useful, History Record and WSV-H entries **may reference commit or session information** —
a correlation, recorded deliberately, in that direction.

```
History Record entry  ──may reference──▶  commit        PERMITTED
commit log            ──reconstructs──▶  semantic history   PROHIBITED
```

The reverse is prohibited, because it would make the record of the *files* into the record of
the *world*.

## What Version Control Is Not, in the Six-Concept Vocabulary

Blueprint §13.7b and RMS §18 separate six concepts that were previously used interchangeably.
Version control is none of them. The table reproduces §13.7b; its sixth row is labelled
**Derivation** rather than the source's *Lineage* because §13.7b itself retires the unqualified
term, and section references are dropped as out of scope here:

| Concept | What it answers | Where it lives |
|---|---|---|
| **Provenance** | Who made this, when, and **why** | An envelope property on the Record |
| **Audit** | Under what approval mode, in which session, by whose act | Recorded within each temporal entry |
| **History** | How this Record's state came to be what it is | Model-owned packaging; World uses the History Record |
| **Revision** | This Record changed, and here is the change | Model-owned |
| **Version** | This is a distinct issued state of the same thing | Model-owned; Issue versions by supersession, never by edit |
| **Derivation** | This came *from* that | Identity operations |

A commit author is not provenance. A commit message is not an audit entry. A commit is not a
revision of a Record. A tag is not a Version in the Issue sense. A merge is not a derivation.

Note the vocabulary rule that governs the last row: **unqualified *lineage* is retired.** Write
`derivation` for identity operations, `LINEAGE` for the World Kind, and *visual derivation* for
asset descent.

## Commit Timestamps Are Not a Canonical Axis

A version-control commit stamp, like a file mtime or a build timestamp, is a technical
timestamp recorded by an external system. **None of those is automatically World Time, Session
Number, or Real-World Time.** I-86: a timestamp produced by an external system is operational
metadata; it becomes World Time, Session Number, or Real-World Time only by being recorded as
such through the mutation path — never by having been generated by a tool.

## Authority

Version control is an external component behind the environment boundary. Blueprint P-31: no
external component — including a version-control system — may hold canonical semantics, define
a kind, own a relationship, adjudicate a mutation, or be the only place a canonical fact exists.
A version-control system may record the commit; it may not redefine authority.

Blueprint §35 lists among what was **rejected**: *version control as a substitute for History
Record or WSV-H*, and *reconstructing semantic history from a commit log*.

## Standing Rules

1. Git history is **not** architectural authority.
2. Git records **that files changed**, never **what canonically changed**.
3. Semantic history is **never** reconstructed from a commit log.
4. Correlation runs **history entry → commit** only, never the reverse.
5. A commit timestamp is **not** a canonical temporal axis.
6. Version control is **not** provenance, audit, history, revision, version, or derivation.
7. Rollback of files is **not** a canon change. Canon is corrected by a new gated change, never
   by a destructive undo.
8. No canonical guarantee may depend on the repository's file history.

Model, temporal mechanism, or mutation path — the History Record, WSV-H and the governed write
path are owned by their own artifacts. Where this document and the Blueprint differ, the
